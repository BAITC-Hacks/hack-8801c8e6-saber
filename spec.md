1. Задача и критерии приёмки
Веб-симулятор по датасету организаторов: пользователь выбирает ровно 5 мероприятий из каталога (для районных — ещё и район) в пределах бюджета 100 условных единиц, движок считает Astana Quality of Life Score (далее Score) по формуле организаторов, AI объясняет результат и предлагает улучшение, проверенное движком.
Правила набора (из датасета организаторов):
1. Решений ровно 5, порядок не важен.
2. Каждое мероприятие не больше одного раза.
3. Для мер типа «Район» район обязателен, для мер типа «Город» не указывается.
4. Сумма стоимостей ≤ 100; остаток не даёт бонуса.
5. Не больше 2 мер из одного направления.
6. Запрещены пары: M1 и M3 (в любых районах); M4 и M7 в одном районе; M5 и M13 в одном районе.
Приёмка — проект готов, когда выполнено всё:
[ ] AC1. docker compose up --build на чистой машине поднимает приложение на http://localhost:8000.
[ ] AC2. Все пользователи получают одинаковые бюджет и данные из data/ (GET /api/state детерминирован).
[ ] AC3. Нарушение любого правила набора: кнопка расчёта в UI неактивна с объяснением, POST /api/scenario возвращает 422 с кодом ошибки из раздела 5.
[ ] AC4. Базовый Score без решений = 52,56; пример организаторов = 56,54. Оба совпадают до 0,01.
[ ] AC5. Один и тот же набор в любом порядке даёт одинаковый Score.
[ ] AC6. Замена любого решения на другое допустимое меняет Score.
[ ] AC7. POST /api/scenario возвращает AI-анализ с полями strengths, risks, consequences, main_tradeoff.
[ ] AC8. POST /api/optimize возвращает набор со Score не ниже исходного и лог проверенных гипотез.
[ ] AC9. Без LLM_API_KEY все эндпоинты работают, AI-поля заполняются фолбэком, в ответе ai_mode: "fallback".
[ ] AC10. pytest проходит, все тесты из раздела 9 реализованы.
[ ] AC11. README содержит все разделы из раздела 11.

5. Движок (app/engine.py)
Реализуй формулу организаторов буквально: эталоны в разделе 9 посчитаны именно так, и их расчёт совпадает с числами организаторов (52,56 и 56,54).
Типы. Decision = {measure_id: str, district_id: str | None}. Набор — список Decision; порядок не важен.
validate(decisions, data, partial=False) -> list[Error] — все ошибки сразу. При partial=True (живое превью) пропускается только проверка количества, допускается 0–5 решений.
Код
Условие
INVALID_COUNT
Решений не ровно 5 (или больше 5 при partial)
DUPLICATE_MEASURE
Одно мероприятие выбрано дважды
UNKNOWN_MEASURE
measure_id нет в каталоге
DISTRICT_REQUIRED
scope: "district", а район пуст или неизвестен
DISTRICT_NOT_ALLOWED
scope: "city", а район передан
BUDGET_EXCEEDED
Сумма cost > 100; в detail сумма и превышение
DIRECTION_LIMIT
Больше 2 мер одного направления; в detail направление
INCOMPATIBLE
Нарушена пара из incompatibilities; в detail пара и reason
simulate(decisions, data) -> Result. Валидацию вызывает API, не simulate.
I = deepcopy(indicators)                    # float, по районам
for d in decisions:                          # 1. эффекты с учётом лага
    m = measure(d.measure_id)
    f = (H - m.lag) / H                      # H = horizon_quarters = 8
    targets = все районы if m.scope == "city" else [d.district_id]
    for t in targets:
        for k, v in m.effects.items():
            I[t][k] += v * f                 # БЕЗ clip на этом шаге
chosen = {d.measure_id: d.district_id for d in decisions}
for s in synergies:                          # 2. синергии, лагом не масштабируются
    if s.pair[0] in chosen and s.pair[1] in chosen:
        I[chosen[s.host]][s.indicator] += s.bonus
for t, k: I[t][k] = clip(I[t][k], 0, 100)    # 3. clip один раз в конце
Clip только в конце — поэтому результат не зависит от порядка решений.
Формулы:
D_d = \sum_{k} w_k \cdot I'_{d,k}
D_{avg} = \sum_d pop_d \cdot D_d
Score = 0.7 \cdot D_{avg} + 0.3 \cdot \min_d D_d - 1.0 \cdot N_{crit}
N_crit — число пар «район × показатель» со значением строго меньше 40 после шага 3 (у Алматы T1 = 40 ровно, это не критично). Коэффициенты 0,7, 40 и 1,0 брать из config. Считать во float, округлять до 2 знаков только в ответе API.
contributions(decisions, data) -> dict[measure_id, float]: Score(все) − Score(набор без этого решения), без валидации. Сумма вкладов не обязана равняться общему приросту — в UI так и подписать.
Result: score_before, score_after, delta, d_avg, d_min, n_crit, critical (список {district_id, indicator, value}), districts (id, name, indicators_before, indicators_after, d_before, d_after), contributions, synergies_applied (список пар), effective_share (для каждого решения (8 − lag)/8), total_cost, budget_left, direction_counts, weakest_district_id (минимальный d_after).
app/optimizer.py — детерминированный поиск без LLM. Опция — пара (мероприятие, район или None для городских): 10 районных мер × 5 районов + 4 городских = 54 опции.
• single_swap_search(decisions) — все наборы, где одно решение заменено на любую другую опцию, не входящую в набор, и прошедшие validate; возвращает лучший.
• hill_climb(decisions, max_rounds=5) — повторяет single_swap_search, пока прирост > 1e-9; возвращает набор и шаги.
• brute_force() — все сочетания 5 из 54 опций, прошедшие validate (694 395 наборов); только для scripts/brute_force.py и тестов, не для API. Должен укладываться в минуту.

Ошибки: HTTP 422, тело {"errors": [{"code": "BUDGET_EXCEEDED", "message": "Превышение бюджета на 8 усл. ед.", "detail": {"total_cost": 108, "budget": 100}}]}. Сообщения на русском, понятные пользователю. Ошибки LLM наружу не пробрасываются: срабатывает фолбэк, код ответа 200.
7. AI-слой (app/ai/)
LLM получает только числа, посчитанные движком, объясняет их, сравнивает наборы и советует — сама ничего не считает; каждый AI-ответ проверяется на бэкенде и при сбое заменяется фолбэком.
7.1. Аналитик (analyst.py)
Один вызов complete_json. Промпты положи в prompts.py дословно.
ANALYST_SYSTEM:
Ты — аналитик городского развития Астаны. Тебе дают результат расчёта симулятора: 5 выбранных мер, их стоимость, лаг и долю эффекта, успевшую реализоваться за 8 кварталов, вклад каждой меры в итоговый Score, сработавшие синергии, показатели районов до и после и список критических значений (ниже 40, штраф 1 балл за каждое).
Как устроен Score: 70% — средний по населению балл районов, 30% — самый слабый район, минус штраф за критические значения.
Правила:
- Опирайся только на переданные числа. Не придумывай данные, районы и меры.
- Каждый пункт strengths, risks и consequences содержит хотя бы одно число из расчёта.
- Упоминай районы, меры и показатели по названию, не по коду.
- Если у меры большой лаг и за горизонт реализовалась только часть эффекта — скажи об этом.
- Если остались критические значения — это первый риск.
- Пиши по-русски, коротко, без канцелярита. Каждый пункт — одно предложение до 25 слов.
- Ответ — только JSON без markdown и пояснений.
Формат:
{"summary": "2–3 предложения", "strengths": ["2–3 пункта"], "risks": ["2–3 пункта"], "consequences": ["2–3 пункта: что будет с районами после горизонта, когда меры с лагом заработают полностью"], "main_tradeoff": "одно предложение", "weakest_district": "id района с минимальным баллом"}
User-сообщение — JSON: {"budget", "total_cost", "score_before", "score_after", "n_crit_before", "n_crit_after", "critical_after": [{district_name, indicator_name, value}], "decisions": [{measure_name, direction_name, district_name, cost, lag, effective_share, contribution}], "synergies_applied", "districts": [{name, population_share, profile, d_before, d_after, indicators_before, indicators_after}], "weakest_district_id"}. Коды показателей заменяй на названия из config.
Проверка ответа: валидный JSON; все поля на месте и не пустые; weakest_district существует. Одна повторная попытка, затем фолбэк.
7.2. Агент-оптимизатор (agent.py)
Вызов run_tools с лимитом AGENT_MAX_TOOL_CALLS (8). Инструменты — обёртки над движком:
Инструмент
Вход
Выход
simulate
{"idea": str, "decisions": [5 Decision]}
{"valid", "score", "n_crit", "total_cost", "errors", "weakest_district", "synergies_applied"}
list_measures
{"direction": str} или {}
Меры: id, name, scope, cost, lag, effects, синергии и несовместимости с их участием
get_district
{"district_id": str}
name, population_share, profile, indicators, D
Каждый вызов simulate записывается в hypotheses (idea, decisions, score, valid, error).
AGENT_SYSTEM:
Ты — агент-оптимизатор бюджета Астаны. Цель: найти набор из 5 мер с максимальным Score при соблюдении правил.
Правила набора: ровно 5 разных мер; бюджет ≤ 100; не больше 2 мер одного направления; для районных мер обязателен район, для городских — нет; запрещены M1 вместе с M3, M4 и M7 в одном районе, M5 и M13 в одном районе.
Как устроен Score: 0.7 × средний балл районов по населению + 0.3 × балл самого слабого района − 1 за каждый показатель ниже 40. Эффект меры реализуется на долю (8 − лаг)/8. Синергии M1+M2, M10+M12, M5+M6 дают бонус.
Как работать:
1. Изучи текущий набор, самый слабый район и критические значения.
2. Сформулируй гипотезу одним предложением и проверь её инструментом simulate. Поле idea — эта гипотеза.
3. Меняй 1–2 меры за раз, чтобы понимать, что даёт прирост.
4. Не утверждай ничего о Score без вызова simulate.
Когда закончишь, ответь только JSON без markdown: {"best_decisions": [5 решений в формате {"measure_id", "district_id"}], "explanation": "3–5 предложений: что изменено и почему это дало прирост, с числами"}
Постобработка: best_decisions прогоняются через validate и simulate движка — Score в ответе всегда из движка. Параллельно считается hill_climb от исходного набора; если он дал больше, возвращается он с source: "baseline". Если лучший найденный Score ниже исходного, возвращается исходный набор с delta: 0.
7.3. llm.py
Anthropic SDK, модель из LLM_MODEL, таймаут LLM_TIMEOUT_SECONDS, temperature=0 для аналитика, 0.3 для агента. Кэш в памяти по sha256 (промпт + вход): одинаковый набор не вызывает LLM повторно. Любое исключение внутри — LLMUnavailable.
7.4. Фолбэк без LLM
Срабатывает, если нет ключа, LLMUnavailable или ответ не прошёл проверку; в ответе ai_mode: "fallback".
• Аналитик: шаблоны по числам. strengths — 2 меры с наибольшим вкладом («Школа + детсад в Нуре: +1,45 к Score») и сработавшие синергии. risks — оставшиеся критические значения; меры с лагом ≥ 3 («реализовано 62% эффекта»); отрицательные эффекты (T1 −2 у безопасных переходов). consequences — районы с наибольшим и наименьшим ростом D; какие меры добавят эффект после горизонта. main_tradeoff — самая дорогая мера и её вклад на 1 усл. ед. в сравнении с самой эффективной. weakest_district — из движка.
• Агент: hill_climb, hypotheses из его шагов (idea — «Заменить <мера> в <район> на <мера> в <район>»), source: "baseline".
